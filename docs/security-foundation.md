# PKI and RBAC foundation

`h3s-certs` generates a ten-year ECDSA cluster CA and one-year API serving/client certificates with explicit ServerAuth or ClientAuth usage. The TLS configuration uses rustls/aws-lc-rs. Client usernames come from the verified certificate's CN and groups from its O attributes, with `system:authenticated` added. The bootstrap administrator is `h3s-admin` in `system:masters`; authorized node issuance uses `system:node:<name>` and `system:nodes`.

The CA, serving certificate/key, and administrator certificate/key are persisted together in `cluster-pki.json`, inside the caller's runtime PKI directory. The directory must have mode 0700 and the file 0600. Bootstrap writes and syncs a temporary file, then installs it only if the destination is absent. Concurrent callers load the winning bundle. Existing malformed, expired, insecure, symlinked, future-version, or key-mismatched material is rejected without silently regenerating the CA. Changing the configured serving SANs also fails if the persisted certificate does not cover them. Back up the complete secret bundle privately; do not place it in source control, a Nix expression/store, or evidence logs.

`ClusterPki::kubeconfig` returns a JSON kubeconfig containing embedded credentials and the trusted CA. The caller must persist it with mode 0600. Missing client certificates are permitted at the TLS layer solely to support public health/version and future bearer authentication. Invalid certificates fail TLS. The HTTP layer must require authentication and authorization for protected paths; neither missing certificates nor caller-supplied headers grant an identity.

`h3s-auth` evaluates stock `k8s-openapi` v1.34 Role, ClusterRole, RoleBinding, and ClusterRoleBinding objects supplied by the API. It denies by default, isolates namespace RoleBindings, resolves User/Group/ServiceAccount subjects, and matches exact resource names, verbs/groups/resources, `*/subresource`, and nonresource URL prefixes. A node certificate does not by itself authorize access to arbitrary objects. The Kubernetes `system:masters` break-glass group is the only built-in unrestricted identity.

The executable API checkpoint now uses verified TLS identities and this RBAC evaluator for its implemented resource handlers. Complete RBAC mutation validation and privilege-escalation prevention, node authorization/NodeRestriction, bootstrap-token exchange, bound ServiceAccount tokens, certificate renewal, and the full cluster workflow remain implementation work. The tests do not claim these capabilities are complete.

Validation includes actual rustls handshake/data exchange, foreign CA and wrong-EKU rejection, hostname verification, expiry, corrupt/key-mismatched bundle rejection, private modes, concurrent bootstrap, and scoped RBAC decisions. The compiler pin remains 1.98.1; minimum Rust support was deliberately raised to 1.88 for rcgen 0.14.10 and is checked separately.

References: [Kubernetes authentication](https://kubernetes.io/docs/reference/access-authn-authz/authentication/), [Kubernetes RBAC](https://kubernetes.io/docs/reference/access-authn-authz/rbac/), and the [v1.34 rule matching contract](https://github.com/kubernetes/kubernetes/blob/v1.34.0/pkg/apis/rbac/v1/evaluation_helpers.go).
