# Admission enforcement checkpoint

The API now enforces Pod Security on normal Pod create, PUT, JSON patch and merge patch before committing registry data. The default is `restricted` in ordinary namespaces (including `default`), and `privileged` in exactly `kube-system`, `kube-public` and `kube-node-lease`. Administrators also pass through this admission check. Namespace writers may select `pod-security.kubernetes.io/enforce` as `restricted`, `baseline` or `privileged`; `enforce-version` accepts `v1.34` or `latest` (currently v1.34). Policy changes persist and affect subsequent requests.

The checker implements baseline host namespace/process/privilege, capabilities, host volume/port/probe, AppArmor, SELinux, proc mount, seccomp and safe-sysctl restrictions. Restricted adds allowed volume sources, no privilege escalation, non-root declarations, explicit seccomp and dropping ALL capabilities with only NET_BIND_SERVICE added. It checks regular, init and ephemeral container entries, including container overrides of Pod security settings. The safe sysctl set includes tcp_rmem/tcp_wmem introduced in v1.32, as verified against the tagged upstream implementation. Linux-only M1 does not grant Windows policy exemptions; user-namespace policy relaxation is not enabled.

Policies are based on [Kubernetes v1.34 standards](https://v1-34.docs.kubernetes.io/docs/concepts/security/pod-security-standards/) and [the v0.34.11 admission implementation](https://github.com/kubernetes/pod-security-admission/tree/v0.34.11/policy). This is the enforcement checkpoint, not complete upstream PodSecurity admission compatibility: warning/audit modes, workload-template warnings, existing-Pod warnings when tightening namespace policy, historical policy versions and Pod-update exemptions remain pending. Unsupported configuration is rejected with 422 rather than ignored. Normal Pod updates currently revalidate the full policy; status writes preserve desired state/metadata and do not re-admit the spec. Deployments/ReplicaSets are accepted independently of their templates' policy; their eventual Pod creations must pass admission. No controller or runtime is certified by these checks.

Namespaced creates also require an existing namespace and fail with 403 if it is terminating. Updates, status reporting and deletion remain available for cleanup. Namespace deletion/finalization controllers remain pending. An empty metadata.namespace uses the endpoint namespace, including clients emitting empty Protobuf scalars. A single API write mutex serializes namespace policy/lifecycle changes, Pod admission and Service allocation through commit; this is single-server coordination, not HA.

The TLS integration tests exercise denied Pod fields, all container classes, supported configuration, restart persistence, inheritance, denied writes retaining the old resourceVersion, and terminating namespace cleanup. The stock-client workload script also tries a privileged Pod in a restricted namespace and verifies rejection without persistence. Its valid Pod fixture explicitly supplies restricted security settings.

[ServiceAccount selection/defaulting and token projection configuration](serviceaccounts.md) are now implemented, with real default-account/public-CA reconciliation through the API. Actual token issuance/refresh, remaining [node admission](node-access.md) coverage, LimitRanger/ResourceQuota, webhooks/CEL and broader field/lifecycle validation remain implementation work before the full runtime acceptance. Do not interpret this checkpoint as permission to bypass them.
