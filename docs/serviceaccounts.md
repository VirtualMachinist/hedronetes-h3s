# ServiceAccount admission and namespace reconciliation

The standalone server now runs a kube-rs `Controller` over Namespaces. It also watches changes to default ServiceAccounts and `kube-root-ca.crt` ConfigMaps, using field selectors and name-restricted permissions. Reconciliation uses authenticated API requests only; `h3s-controllers` has no storage dependency. It creates a missing default account, publishes the public cluster CA, repairs a deleted account or altered CA, and preserves existing account configuration and unrelated ConfigMap data/metadata. It skips terminating namespaces and retries API failures. Startup lists existing namespaces, so restarting the server resumes reconciliation without replacing existing identities.

The controller uses an in-memory X.509 identity, `system:h3s:namespace-controller`, issued from the persistent CA at server startup. Its ClusterRole permits namespace read/list/watch, default-account read/list/watch, root-CA ConfigMap read/list/watch/update, and account/ConfigMap creation. Kubernetes create authorization cannot be restricted by resourceNames, so those create grants are collection-level; it cannot read Secrets, create Pods, delete accounts, edit namespaces or mutate RBAC. The private controller key is not written to disk or logs. API contract tests use explicit account fixtures without background writes; separate integration tests start the actual controller and verify repair and permissions over TLS.

Pod create admission requires its selected ServiceAccount in the same namespace. The default is `default`; deprecated `serviceAccount` and current `serviceAccountName` are normalized consistently and conflicting values fail. Missing/terminating accounts and unsupported mirror Pods are rejected before persistence. No service account is synthesized by admission: after creating a Namespace, clients may need to retry while its controller creates the default account.

Empty Pod imagePullSecrets inherit the account list; explicit lists are preserved. Pod automountServiceAccountToken overrides the account setting, then defaults to true. When enabled, admission adds a read-only projected volume for the bound token, public CA ConfigMap and namespace field, mounting it in regular and init containers that do not already mount the conventional path. Existing mount-path overrides and matching kube-api-access volume names are respected. Updates preserve the injected configuration rather than generating duplicate volumes. Accounts opting into `kubernetes.io/enforce-mountable-secrets` restrict secret-volume, projected-secret, environment and image-pull references. This reference check does not fetch secret contents.

**TokenRequest issuance, bearer authentication, audience/bound-object validation and kubelet token refresh/mounting remain unimplemented.** The projected volume is desired configuration, not evidence of a usable token. Scheduling, actual containers, node restrictions and full runtime acceptance remain pending.

Dependency choice: kube 2.0.1 shares k8s-openapi 0.26 and the existing v1.34 resource types. Its default features are disabled; rustls uses AWS-LC. The lockfile pins enum-ordinalize and its derive crate to 4.3.2 because 4.4.2 requires Rust 1.89; the project retains its separately tested Rust 1.88 minimum. A coordinated kube/k8s-openapi upgrade can follow when needed; blindly replacing kube with 4.x would change the API type dependency boundary.

The stock-client `integration/tower/check-serviceaccounts.py` checks actual default-account recreation, public-CA repair, pull-secret/automount behavior, projected-volume injection and missing-account rejection. It uses an existing project namespace, refuses to delete an operator-configured default account, removes unique Pod/account fixtures, and restores the public CA if the repair test fails. Controller-owned default accounts and CA ConfigMaps remain as normal cluster state.

Behavior reference: [Kubernetes v1.34.11 ServiceAccount admission](https://github.com/kubernetes/kubernetes/blob/v1.34.11/plugin/pkg/admission/serviceaccount/admission.go). This checkpoint does not claim complete upstream admission or controller conformance.

The first live upgrade probe exposed an existing-data bug: a Namespace originally created through Protobuf retained metadata.namespace="". kube-rs keyed its cached Namespace as namespace Some("") while child-event mapping used None, so default-account recreation missed the cached object. API reads now normalize empty namespace metadata, including LIST/WATCH of older stored objects; new cluster-scoped writes omit it. A persisted-state regression starts the real controller over that older shape and verifies repair. The original failed probe remains evidence; newly created JSON namespaces alone did not expose this case.
